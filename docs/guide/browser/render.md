# 浏览器渲染流程与重排重绘

> 面试频率：⭐⭐⭐⭐⭐ | 关联考点：事件循环、requestAnimationFrame、性能优化、合成层

## 面试回答（开口版）

如果面试官问「浏览器是如何渲染页面的」，可以这样回答：

> 当浏览器的网络线程收到 HTML 文档后，会产生一个**渲染任务**，传递给渲染主线程的消息队列；在事件循环机制的作用下，渲染主线程取出任务开启渲染流程。整个流程是一条组织严密的生产流水线，分为八个阶段：**HTML 解析、样式计算、布局、分层、绘制、分块、光栅化、画**，每个阶段都有明确的输入输出，上一阶段的输出就是下一阶段的输入。HTML 解析得到 DOM 树和 CSSOM 树；样式计算得到带样式的 DOM 树（Computed Style）；布局得到布局树（几何信息）；分层得到图层树；绘制生成绘制指令；分块把图层切成图块；光栅化把图块转成位图；最后由**合成线程**交给 GPU 画到屏幕上。理解了这条流水线，重排重绘就简单了：改几何信息从**布局**阶段重走，改颜色从**绘制**阶段重走，而 transform / opacity 只影响最后的**合成**——由独立线程处理，性能最好。

**答题要点：** 渲染任务怎么来的 -> 八阶段流水线 -> 每阶段输入输出 -> 重排/重绘/合成对应从哪个阶段重走

## 一、宏观流程：从输入 URL 到页面展示

```text
1. URL 解析（补协议、编码、HSTS）
2. DNS 解析（浏览器缓存 -> 系统 -> 路由器 -> 运营商 -> 递归查询）
3. TCP 三次握手（HTTPS 再加 TLS 握手）
4. 发送 HTTP 请求（可能命中缓存：强缓存不发请求，协商缓存可能 304）
5. 服务器返回响应
6. 网络线程收到 HTML -> 产生渲染任务 -> 传递给渲染主线程的消息队列
7. 事件循环机制下，渲染主线程取出渲染任务，开启渲染流水线
8. 执行脚本、绑定事件，页面可交互
```

## 二、渲染流水线总览：八个阶段（含执行线程）

```text
HTML 文档
   |
   v
1. HTML 解析   --> DOM 树 + CSSOM 树    【渲染主线程】（外部 CSS/JS 下载由预解析线程并行完成）
   |
   v
2. 样式计算    --> 带样式的 DOM 树      【渲染主线程】
   |
   v
3. 布局        --> 布局树              【渲染主线程】
   |
   v
4. 分层        --> 图层树              【渲染主线程】
   |
   v
5. 绘制        --> 绘制指令列表         【渲染主线程】（只生成指令，还不真正画）
   |
   v
6. 分块        --> 图块                【合成线程】（视口附近的图块优先）
   |
   v
7. 光栅化      --> 位图                【光栅化线程池】（多线程并行 + GPU 加速）
   |
   v
8. 画（合成）  --> 显示到屏幕          【合成线程 + GPU 进程】
```

**线程分工总表：**

| 线程 / 进程 | 负责的阶段 | 关键特点 |
| --- | --- | --- |
| **渲染主线程** | 1 HTML 解析、2 样式计算、3 布局、4 分层、5 绘制 | JS 也在这个线程执行——长任务会卡住整条流水线（前 5 步全部暂停） |
| **预解析线程** | 配合阶段 1：提前下载外部 CSS / JS | 让主线程解析 HTML 不被资源下载阻塞 |
| **合成线程** | 6 分块、8 画（生成绘制四边形并提交 GPU） | **独立于主线程**——主线程卡死时滚动、transform 动画依然流畅 |
| **光栅化线程池** | 7 光栅化 | 多个线程按优先级并行，把图块转成位图 |
| **GPU 进程** | 最终输出 | 接收合成线程提交的位图信息，把各层合成并显示到屏幕 |

**核心思想：每个阶段都有明确的输入输出，上一个阶段的输出成为下一个阶段的输入——一套组织严密的生产流水线。**

**主线程与合成线程的分界线**：前 5 步在渲染主线程，后 3 步交给合成线程（配合光栅化线程池和 GPU）。这条分界线正是「transform 动画为什么不受 JS 卡顿影响」的答案。
## 三、逐阶段详解

### 3.1 HTML 解析：得到 DOM 树和 CSSOM 树

解析过程中遇到 CSS 就解析 CSS，遇到 JS 就执行 JS。为了提高效率，浏览器在开始解析前会启动一个**预解析线程**，率先下载 HTML 中的外部 CSS 文件和外部 JS 文件。

**CSS 为什么不阻塞 HTML 解析？**

主线程解析到 `<link>` 位置时，如果外部 CSS 还没下载解析好，主线程**不会等待**，继续解析后续 HTML——因为下载和解析 CSS 的工作是在**预解析线程**中进行的。

**JS 为什么阻塞 HTML 解析？**

主线程解析到 `<script>` 位置时，会**停止解析 HTML**，等待 JS 文件下载好、全局代码解析执行完成后才能继续——因为 JS 可能修改当前的 DOM 树（`document.write`、增删节点），DOM 树的生成必须暂停。

```text
解析完成 --> 得到 DOM 树 + CSSOM 树
（浏览器默认样式、内部样式、外部样式、行内样式全部包含在 CSSOM 树中）
```

`defer` / `async` 就是为了缓解 JS 阻塞：

| 属性 | 下载 | 执行时机 | 是否阻塞解析 |
| --- | --- | --- | --- |
| 无 | 阻塞 | 下载完立即执行 | 阻塞 |
| async | 预解析线程并行下载 | 下载完立即执行 | 仅执行瞬间阻塞 |
| defer | 预解析线程并行下载 | DOM 解析完后按序执行 | 不阻塞 |

### 3.2 样式计算：得到带样式的 DOM 树

主线程**遍历 DOM 树**，依次为树中的每个节点计算出它的**最终样式（Computed Style）**。

这一过程中，很多预设值会变成**绝对值**：

```text
red        -> rgb(255, 0, 0)     预设值 -> 绝对值
2em        -> 32px               相对单位 -> 绝对单位
font: xx-large -> font-size: 32px 具体化
```

为什么必须绝对化？——后面的布局阶段只需要拿着具体数值做数学计算，不用再理解各种写法。

在 DevTools 的 Elements -> Computed 面板里看到的，就是这一步的输出。

### 3.3 布局：得到布局树

主线程**遍历带样式的 DOM 树**，依次计算每个节点的**几何信息**：宽、高、相对包含块的位置。

输出是**布局树（Layout Tree）**。注意：**DOM 树和布局树并非一一对应**：

| 情况 | 在 DOM 树？ | 在布局树？ | 原因 |
| --- | --- | --- | --- |
| 普通节点 | 是 | 是 | 正常 |
| `display: none` 的节点 | 是 | **否** | 没有几何信息，不参与布局 |
| 伪元素 `::before/::after` | **否** | 是 | DOM 树中不存在，但有几何信息 |
| 匿名行盒 / 匿名块盒 | 否 | 是 | 布局需要自动生成的包装盒 |

这也是「**为什么操作 DOM 代价大**」的原因之一：一次修改可能引起 DOM 树、样式树、布局树三层结构的重新计算。

### 3.4 分层：得到图层树

主线程为布局树的每个节点决定它属于哪个**图层（Layer）**，输出**图层树（Layer Tree）**。

**为什么要分层？**

1. 某一层变化时只需重新处理这一层，不影响其他层；
2. 最终合成阶段可以**并行**处理各层。

**什么情况会被单独分层？**

- 层叠上下文：定位元素 + z-index、opacity < 1、transform、filter；
- `will-change: transform / opacity`；
- 3D 变换（translateZ）、`position: fixed`；
- video、canvas、WebGL。

::: warning 层爆炸
每个图层都占显存，光栅化也有成本。大量元素强行分层（乱加 will-change / translateZ(0)）会「层爆炸」，反而更卡。**确定要做动画的元素才分层，动画结束移除**。
:::

### 3.5 绘制：得到绘制指令

主线程为**每个图层**单独生成**绘制指令列表（Paint Records）**——一系列「在什么坐标画什么」的指令：

```text
指令1：在 (0, 0) 画一个 300x150 的背景色矩形
指令2：在 (0, 0) 画边框
指令3：在 (10, 20) 用 16px 字体画文本 "Hello"
...
```

注意：这一步**只是生成指令，还没有真正画图**。绘制顺序由**层叠上下文**规则决定（这也是 z-index 参与的环节）。

### 3.6 分块：把图层切成图块

绘制完成后，主线程把每个图层交给**合成线程**。

合成线程将图层划分为一个个小的**图块（Tile）**，通常是 256x256 或 512x512 的大小。同时会给图块划分**优先级**：

- **视口附近的图块优先**处理；
- 远离视口的图块稍后处理。

为什么分块？——一个长页面可能非常大，一次性光栅化整页太浪费；只把用户看得见的区域先变出来，滚到哪画到哪。

### 3.7 光栅化：图块变位图

光栅化在**光栅化线程池**中执行（多个光栅化线程并行），按优先级把每个图块转成**位图**——即把指令真正变成每个像素的颜色值。

现代浏览器使用 **GPU 加速光栅化**，位图通常保存在 GPU 内存中。

```text
绘制指令 + 图块区域 --> GPU 光栅化 --> 位图（像素数组）
```

### 3.8 画（合成）：最终显示到屏幕

所有图块光栅化完成后，合成线程收集每个图块的**绘制四边形（Draw Quad）**信息——包含「哪张位图、画在屏幕什么位置、经过什么变换」——提交给浏览器主进程（GPU 进程），由 GPU 把各层位图合成最终图像，**显示到屏幕上**。

**关键：这一步不在渲染主线程执行。**

所以即使 JS 把主线程卡死了：

- 滚动依然流畅（滚动由合成线程处理）；
- transform / opacity 动画依然流畅（只影响合成阶段的 quad 计算）。

这就是「为什么动画要用 transform」的根本原因。

## 四、一帧的完整组成（流水线与事件循环）

```text
一帧（约 16.7ms @ 60fps）
+--------------------------------------------------+
| 1. 执行一个宏任务（task）                          |
| 2. 清空全部微任务（microtask）                     |
| 3. 必要时进入渲染阶段（即上面的流水线）：           |
|    a. requestAnimationFrame 回调                  |
|    b. 样式计算 -> 布局 -> 分层 -> 绘制            |
|       -> 分块 -> 光栅化 -> 画                     |
| 4. 若还有剩余时间：requestIdleCallback            |
+--------------------------------------------------+
```

三个关键结论：

1. **rAF 回调在渲染流水线之前执行**，做动画用它而不是 setTimeout；
2. 长任务超过一帧预算会**推迟渲染**，表现为掉帧、卡死；
3. `requestIdleCallback` 在一帧空闲时执行，适合不紧急的计算。

## 五、重排、重绘、合成：从流水线哪个阶段重走

理解了八阶段流水线，三者区别一目了然：

| 改动类型 | 重走阶段 | 代价 |
| --- | --- | --- |
| **重排（回流）** 改 width/top/margin/font-size | 布局 -> 分层 -> 绘制 -> 分块 -> 光栅化 -> 画 | 最大 |
| **重绘** 改 color/background/visibility | 绘制 -> 分块 -> 光栅化 -> 画 | 中 |
| **合成** 改 transform / opacity | 只影响合成阶段（画） | 最小 |

```text
HTML解析 -> 样式计算 -> [布局] -> [分层] -> [绘制] -> [分块] -> [光栅化] -> [画]
                         ^                  ^                            ^
                         重排从这里重走       重绘从这里重走                 合成只重走这里
```

**重要细节：修改后不会立即重排**——渲染引擎先把受影响节点标记为 dirty（脏标记），到下一次布局时统一增量处理；只有「写完立刻读布局属性」才会强制立即重排（布局抖动）。

## 六、属性触发表：改什么走哪条路径

| 你改的属性 | 触发阶段 | 性能 |
| --- | --- | --- |
| color / background / visibility / box-shadow | 绘制 -> 画 | 中 |
| width / height / top / left / margin / font-size | 布局 -> 画 | 差 |
| **transform / opacity** | **只合成** | **好** |
| scrollTop（滚动） | 只合成 | 好 |

```js
// 同一个动画的两种实现
el.style.left = x + 'px'                  // 每帧重排，容易掉帧
el.style.transform = `translateX(${x}px)` // 只合成，丝滑
```

## 七、关键渲染路径（Critical Rendering Path）

**定义**：从收到 HTML 到**首次渲染出内容（FCP）**必须经过的最短路径。优化目标：**关键资源数最少、关键字节数最小、路径长度最短**。

| 手段 | 做法 | 效果 |
| --- | --- | --- |
| 关键 CSS 内联 | 首屏样式（< 14KB）写进 HTML | 省一次 CSS 请求，立即渲染 |
| 非关键 CSS 异步 | `<link media="print" onload="this.media='all'">` | 不阻塞首屏 |
| 脚本延迟 | 全部 defer / async | 不阻塞 HTML 解析 |
| 关键资源预加载 | `<link rel="preload" as="font">` | 提前下载字体 / 首图 |
| 减少串联请求链 | 避免「CSS 引字体、字体再引图标」层层等待 | 缩短路径长度 |

## 八、首屏性能指标：FCP / LCP / CLS

| 指标 | 含义 | 与流水线的关系 | 优化手段 |
| --- | --- | --- | --- |
| **FCP** 首次内容绘制 | 第一个内容出现 | 流水线第一次输出到屏幕 | 关键 CSS 内联、SSR、骨架屏 |
| **LCP** 最大内容绘制 | 主内容渲染完成 | 大图 / 大文本块的光栅化完成 | 图片 preload、首屏图不懒加载、CDN |
| **CLS** 累积布局偏移 | 页面意外「跳动」 | **布局不稳定 = 重排的外在表现** | 图片设宽高、占位预留 |
| **TBT / INP** 交互响应 | 主线程被长任务占用 | 长任务吃掉一帧的渲染预算 | 拆任务、Web Worker |

CLS 经典案例——图片加载完成后把下面的内容挤下去，就是一次用户可见的重排：

```html
<!-- 坏：加载完成后布局跳动 -->
<img src="banner.png" />
<!-- 好：提前占位，不产生偏移 -->
<img src="banner.png" width="800" height="400" />
<!-- 或 CSS：aspect-ratio: 2 / 1 -->
```

## 十、性能优化实战（总结版）

1. **动画三件套**：只用 `transform` / `opacity` + rAF；
2. **读写分离**：布局属性先批量读，再批量写（防布局抖动）；
3. **批量修改**：`DocumentFragment`、一次性替换 innerHTML、class 切换代替多次 style；
4. **脱离文档流**：动画元素 `position: absolute/fixed`，重排不影响兄弟节点；
5. **避免隐式布局读取**：缓存 `offsetTop` 等值，不在循环里反复读；
6. **长任务拆分**：超过 50ms 的任务用 Web Worker 或分帧执行；
7. **屏幕外内容跳过渲染**：

```css
.long-list-item {
  content-visibility: auto;      /* 屏幕外不参与渲染 */
  contain-intrinsic-size: 200px; /* 预估高度，防滚动条跳动 */
}
```

```js
// DocumentFragment：1000 个节点只触发一次重排
const frag = document.createDocumentFragment()
for (let i = 0; i < 1000; i++) {
  const li = document.createElement('li')
  li.textContent = i
  frag.appendChild(li)
}
ul.appendChild(frag)
```

| --- | --- |
| 浏览器怎么渲染页面？ | 网络线程收到 HTML 产生渲染任务 -> 消息队列 -> 渲染主线程取出执行：HTML 解析 -> 样式计算 -> 布局 -> 分层 -> 绘制 -> 分块 -> 光栅化 -> 画 |

| JS 为什么阻塞 HTML 解析？ | JS 可能修改 DOM 树，必须等下载执行完再继续生成 DOM |
| 样式计算做什么？ | 遍历 DOM 树算出每个节点最终样式，预设值绝对化（red -> rgb、em -> px） |
| DOM 树和布局树有什么区别？ | display:none 在 DOM 不在布局；伪元素、匿名盒在布局不在 DOM |
| 为什么要分层？ | 单层变化不影响其他层；合成阶段可并行处理各层 |
| 绘制阶段产出什么？ | 绘制指令列表（Paint Records），不是直接画像素 |
| 光栅化在哪做？ | 光栅化线程池，GPU 加速，把图块转成位图 |
| 主线程卡死还能滚动吗？ | 能，滚动和合成都不在主线程（合成线程处理） |
| 重排/重绘/合成分别从哪重走？ | 重排从布局、重绘从绘制、合成只重走最后的画 |
| rAF 为什么适合动画？ | 回调在流水线执行前、跟随刷新率，本帧就能画出来 |
| transform 为什么快？ | 只影响合成阶段的 quad 计算，GPU 处理，不占主线程 |
| CLS 怎么优化？ | 图片/广告位预留尺寸（width/height 或 aspect-ratio） |
| 怎么用 DevTools 看重绘？ | Rendering 面板开 Paint flashing，绿色即重绘区域 |
| will-change 慎用的原因？ | 每层占显存，滥用导致层爆炸 |

## 十二、速记卡

```text
1. 流水线：HTML解析 -> 样式计算 -> 布局 -> 分层 -> 绘制 -> 分块 -> 光栅化 -> 画
2. 样式计算：red->rgb、em->px，得到 Computed Style
3. 布局树 != DOM 树：display:none 不进，伪元素/匿名盒会进
4. 分层好处：单层变化隔离 + 合成并行；滥用 = 层爆炸

8. 主线程卡死，滚动和 transform 动画依然流畅（合成线程的功劳）
```
