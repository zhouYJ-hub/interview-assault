# 网络基础

> 面试频率：⭐⭐⭐⭐⭐ | 覆盖：完整请求流程、DNS、TCP、HTTPS、HTTP 版本、状态码、缓存策略

## 面试回答（开口版）

如果面试官问「从输入 URL 到页面展示，网络层面发生了什么」，可以这样回答：

> 先做 URL 解析，然后 **DNS 解析**把域名变成 IP——先查浏览器和系统缓存，没有再问本地 DNS 服务器，它通过「根 -> 顶级域 -> 权威」的**迭代查询**拿到结果。接着和服务器建立 **TCP 连接**，经过**三次握手**确认双方收发能力；HTTPS 还要再完成 **TLS 握手**：服务端下发证书，双方用非对称加密协商出对称密钥，之后所有数据都用密钥加密传输。然后浏览器构建 **HTTP 请求**发送，服务器处理后返回响应；返回前可能命中**缓存**——强缓存有效直接 200 from cache 不发请求，过期了走协商缓存，带 ETag 或 Last-Modified 去验证，没变就 304。拿到响应后浏览器进入渲染流水线（见《渲染流程》专题），连接默认 keep-alive 保持复用，断开时 TCP **四次挥手**。

**答题要点：** URL 解析 -> DNS 迭代查询 -> TCP 三次握手 -> TLS -> HTTP 请求响应 -> 缓存介入 -> 渲染 -> 四次挥手

## 一、一个完整的请求流程（总览）

```text
[1] URL 解析
     |  补协议、编码校验
     v
[2] DNS 解析
     |  域名 -> IP（多级缓存 -> 迭代查询）
     v
[3] TCP 三次握手
     |  建立可靠连接
     |  (HTTPS? 额外完成 TLS 握手)
     v
[4] 发送 HTTP 请求
     |  请求行 + 请求头 + 请求体
     v
[5] 缓存判定（客户端 + 服务端）
     |
     |-- 强缓存有效 -------> 200 from cache（不发网络请求，到此结束）
     |
     |-- 强缓存过期
     |      |
     |      v
     |   协商缓存验证
     |      |-- 资源没变 -----> 304（继续用本地缓存）
     |      |-- 资源变了 -----> 200 + 新资源
     v
[6] 浏览器渲染
     |  解析 HTML -> 渲染流水线（见渲染专题）
     v
[7] 连接管理
        keep-alive 复用连接 / 断开时 TCP 四次挥手
```

## 二、DNS 域名解析

**作用**：把 `www.example.com` 翻译成服务器 IP `93.184.216.34`。

### 2.1 查询顺序图（缓存优先）

```text
浏览器
  |
  | 1. 查本地缓存
  |    浏览器 DNS 缓存 -> 操作系统缓存 -> hosts 文件
  |
  | 都没有？问本地 DNS 服务器（运营商）
  v
本地 DNS 服务器
  |
  | 2. 迭代查询：
  |    问 根服务器        "www.example.com 谁管?"
  |<-- "去问 .com 顶级域服务器"
  |
  |    问 .com 服务器
  |<-- "去问 example.com 权威服务器"
  |
  |    问 权威服务器
  |<-- "IP 是 93.184.216.34"
  |
  v
返回给浏览器，结果逐级写入缓存
```

### 2.2 递归查询 vs 迭代查询

| | 递归查询 | 迭代查询 |
| --- | --- | --- |
| 谁在问 | 浏览器 -> 本地 DNS：「帮我查到底」 | 本地 DNS 自己逐级问根 -> .com -> 权威 |
| 结果 | 本地 DNS 最终给最终答案 | 每级只告诉你「下一级去问谁」 |

### 2.3 DNS 优化

```html
<!-- 预解析：提前对第三方域名做 DNS 查询 -->
<link rel="dns-prefetch" href="//cdn.example.com" />

<!-- 预连接：DNS + TCP + TLS 一起提前做，比 prefetch 更激进 -->
<link rel="preconnect" href="//cdn.example.com" />

<!-- CDN：把资源部署到离用户最近的节点，DNS 解析返回就近 IP -->
```

## 三、TCP：三次握手与四次挥手

### 3.1 三次握手（建立连接）

```text
客户端                                服务器
  |                                    |
  | ---- SYN（我想建立连接）----------> |  第 1 次
  |     seq=x                          |  客户端 -> SYN_SENT
  |                                    |
  | <-- SYN + ACK（可以，我也准备好）--- |  第 2 次
  |     seq=y, ack=x+1                 |  服务器 -> SYN_RCVD
  |                                    |
  | ---- ACK（收到，开始传数据）-------> |  第 3 次
  |     ack=y+1                        |  双方 -> ESTABLISHED
  |                                    |
  | ============ 开始传输数据 ========= |
```

**为什么是三次，不是两次？**

```text
两次握手做不到的事:
  1. 无法确认「服务端的发送 -> 客户端的接收」这条链路
     第 1 次确认: 客户端能发、服务端能收
     第 2 次确认: 服务端能发、客户端能收  ← 两次缺这个
     第 3 次确认: 客户端能收(向服务端证明)

  2. 无法防历史失效连接:
     旧的 SYN 迟到抵达 -> 服务端建连占资源
     第三次 ACK 客户端可拒绝 -> 浪费止于服务端
```

### 3.2 四次挥手（断开连接）

```text
主动方（通常是客户端）                被动方（服务器）
  |                                      |
  | ---- FIN（我数据发完了）----------->  |  第 1 次
  |                                      |  主动方 -> FIN_WAIT_1
  |                                      |
  | <-- ACK（知道，我可能还有数据）-----  |  第 2 次
  |                                      |  被动方 -> CLOSE_WAIT
  |                                      |  主动方 -> FIN_WAIT_2
  |                                      |  (被动方继续发送剩余数据)
  |                                      |
  | <--- FIN（我也发完了）--------------  |  第 3 次
  |                                      |  被动方 -> LAST_ACK
  |                                      |
  | ---- ACK（好，断开）--------------->  |  第 4 次
  |                                      |  主动方 -> TIME_WAIT
  |                                      |  被动方收到 ACK 即关闭
  |                                      |
  |  主动方等待 2MSL 后关闭               |
```

**为什么挥手要四次？** 半关闭概念：

```text
握手: 双方都还没数据, SYN+ACK 可以合并在一次发送 -----> 3 次
挥手: 被动方收到 FIN 时可能还有数据没发完
      ACK 必须马上回, FIN 要等数据发完再发
      两个分开发送 ---------------------------------> 4 次
```

### 3.3 keep-alive：连接复用

```text
无 keep-alive (HTTP/1.0):
  [握手]--请求A--[挥手] [握手]--请求B--[挥手] [握手]--请求C--[挥手]
  每次 1~2 个 RTT 白白浪费

keep-alive (HTTP/1.1 默认):
  [握手]--请求A--请求B--请求C--[挥手]
  省掉重复握手, 但同连接请求要排队(队头阻塞)
```

## 四、HTTP 与 HTTPS 的区别

### 4.1 结构对比图

```text
HTTP 请求的数据流:

  应用层:  [ GET /api HTTP/1.1 ... ]
                 |
                 v  明文直接下交
  传输层:  TCP 传输明文 --------------> 中间人可 窃听 / 篡改 / 冒充


HTTPS 请求的数据流:

  应用层:  [ GET /api HTTP/1.1 ... ]
                 |
                 v  TLS 加密
  安全层:  [ 8J3f$#kL...x9 ] 密文
                 |
                 v
  传输层:  TCP 传输密文 --------------> 中间人只能看到乱码
```

### 4.2 完整对比表

| 对比项 | HTTP | HTTPS |
| --- | --- | --- |
| 全称 | 超文本传输协议 | HTTP over TLS/SSL |
| URL 前缀 | `http://` | `https://`（地址栏带锁标志） |
| 默认端口 | **80** | **443** |
| 传输内容 | **明文** | **加密**（对称加密） |
| 三大风险 | 窃听、篡改、冒充 | TLS 全部解决（加密 / 完整性校验 / 证书） |
| 证书 | 不需要 | 需要 **CA 机构**颁发的证书 |
| 连接建立 | TCP 三次握手 | TCP 握手 + **TLS 握手**（多 1~2 个 RTT） |
| 性能 | 无加密开销 | 略慢（握手 + 加解密，现代硬件已基本无感） |
| SEO | 无加成 | 搜索引擎排名信号之一 |

### 4.3 一句话记忆

> HTTP 是「明信片」——谁都能看、能改；HTTPS 是「加密信封 + 签名」——内容看不到、改了会被发现、身份可验证。

## 五、HTTPS 与 TLS 握手

**HTTPS = HTTP + TLS**，核心思想：**用非对称加密交换密钥，用对称加密传输数据**。

- 非对称加密安全但慢 -> 只在握手阶段用；
- 对称加密快 -> 用来保护之后的所有通信。

### 5.1 简化版 TLS 握手时序图

```text
客户端                                   服务器
  |                                        |
  | --- 1. ClientHello ------------------> |
  |     (TLS 版本 + 支持的加密套件 + 随机数C) |
  |                                        |
  | <-- 2. ServerHello + 证书 ------------- |
  |     (选定套件 + 随机数S + CA 签发证书)    |
  |                                        |
  |     3. 客户端验证证书                    |
  |        (用内置 CA 公钥验签, 防冒充)        |
  |                                        |
  | --- 4. 密钥交换信息 -------------------> |
  |     (预主密钥用服务器公钥加密传输)          |
  |                                        |
  |     5. 双方用 随机数C+随机数S+预主密钥     |
  |        各自算出相同的「会话密钥」           |
  |                                        |
  | === 6. 之后全部数据用会话密钥对称加密 ===== |
```

### 5.2 证书怎么防冒充？

```text
中间人攻击(无证书验证):
  浏览器 <--> [中间人 假装服务器] <--> 真服务器

有 CA 证书验证:
  服务器证书由 CA 私钥签名
  -> 浏览器用内置的 CA 公钥验签
  -> 中间人没有 CA 私钥, 无法伪造合法证书
  -> 验签失败, 浏览器红色警告
```

## 六、HTTP 版本演进

### 6.1 四个版本的连接方式图

```text
HTTP/1.0: 每个请求一条新连接
  [握手]---请求A---[挥手]
  [握手]---请求B---[挥手]
  [握手]---请求C---[挥手]
  问题: 重复握手开销大


HTTP/1.1: keep-alive 长连接(默认开启)
  [握手]---A---B---C---[挥手]
  改进: 复用连接
  问题: 同一连接的请求要排队(队头阻塞)


HTTP/2: 多路复用
  [握手]---[A2|B1|A1|C1|B2|C2]---[挥手]
  改进: 请求拆成带编号的二进制帧, 帧交错传输
        + HPACK 头部压缩 + 服务器推送
  问题: TCP 层丢包, 后面所有帧都得等(传输层队头阻塞)


HTTP/3: QUIC(基于 UDP)
  改进: 0-RTT 快速建连
        彻底解决传输层队头阻塞
        网络切换(WiFi->4G)不断连
```

### 6.2 队头阻塞对比图

```text
HTTP/1.1 一条连接排队:
  请求A(慢, 3s) -> 请求B(快, 100ms) -> 请求C
                    ^ B 明明很快, 却要等 3.1s 才开始  ← 队头阻塞

HTTP/2 多路复用:
  A、B、C 的帧交错传输, 按编号重组
  B 不用等 A 全部完成                    ← 应用层解决

HTTP/2 的遗留问题:
  TCP 丢了一个包 -> 后面所有流都要等重传   ← 传输层队头阻塞
  HTTP/3 用 QUIC: 每个流独立, 丢包只影响自己 ← 彻底解决
```

## 七、HTTP 状态码

### 7.1 分类记忆图

```text
状态码五大类（按「谁的责任」记忆）
|
+-- 1xx 信息类 -------- 请求还在进行中
|     101 协议升级
|       WebSocket 建连: 客户端发 Upgrade: websocket
|       服务器同意返回 101, 之后通信切换到 WebSocket 协议
|
+-- 2xx 成功类 -------- 请求正常处理完
|     200 成功          最常见: GET / POST 正常返回
|     201 已创建        POST 创建资源成功, 新地址在 Location 头
|     204 无内容        DELETE / PUT 成功, 响应体为空
|     206 部分内容      Range 请求: 视频拖进度条 / 断点续传
|
+-- 3xx 重定向类 ------ 要去别的地方拿
|     301 永久重定向    换域名: 搜索引擎把权重转移到新地址
|     302 临时重定向    登录后跳回原页面 / 短链跳转
|     304 缓存有效      协商缓存命中: "你的缓存还能用"（无资源体）
|     307 临时 + 不改方法  302 严格版: 重定向后不许把 POST 变 GET
|     308 永久 + 不改方法  301 严格版
|
+-- 4xx 客户端错误类 --- 你的请求有问题
|     400 参数错误      前端传参格式不对 / 缺字段
|     401 未认证        没登录 / token 过期 -> 引导去登录
|     403 禁止访问      知道你是谁, 但没权限（和 401 区别高频）
|     404 资源不存在    路径写错 / 资源被删
|     405 方法不允许    对只读接口发了 POST
|     429 请求太频繁    触发限流, 响应头常带 Retry-After
|
+-- 5xx 服务器错误类 --- 服务器自身出问题
      500 内部错误      后端代码抛了未捕获异常
      502 网关错误      Nginx 收到后端无效响应 / 后端进程挂了
      503 服务不可用    过载 / 维护中
      504 网关超时      Nginx 等后端响应超时（后端太慢）
```

### 7.2 高频状态码详解

| 状态码 | 含义 | 备注 |
| --- | --- | --- |
| 200 | 成功 | |
| 204 | 成功但无返回体 | 常用于 DELETE 成功 |
| 206 | 部分内容 | Range 断点续传 / 视频拖动进度条 |
| 301 | 永久重定向 | 搜索引擎更新收录地址 |
| 302 | 临时重定向 | 登录后跳转 |
| **304** | 协商缓存命中 | 服务器告诉浏览器「缓存还能用」 |
| 400 | 请求参数错误 | |
| 401 | 未认证 | 缺少 / 过期 token |
| 403 | 已认证但无权限 | 401 是「你是谁」，403 是「你知道你是谁，但不行」 |
| 404 | 资源不存在 | |
| 429 | 请求过于频繁 | 限流 |
| 500 | 服务器内部错误 | 代码抛异常 |
| 502 | 网关错误 | 后端挂了 / 返回格式不对 |
| 503 | 服务不可用 | 过载 / 维护 |
| 504 | 网关超时 | 后端响应太慢 |

## 八、强缓存（不发请求）

### 8.1 工作过程图

```text
首次请求:
  浏览行 ------ 请求 ------> 服务器
  浏览器 <----- 200 资源 ---- 服务器
  (存入缓存, 记下 Cache-Control: max-age=3600)

有效期内再次请求:
  浏览器 -> [本地缓存] 直接使用, 请求都不发
  DevTools 显示: 200 (from memory cache / disk cache)

有效期过后(强缓存过期):
  走协商缓存(见下一节)
```

### 8.2 Expires（HTTP/1.0，了解）

```http
Expires: Wed, 29 Oct 2027 08:00:00 GMT
```

缺点：依赖**客户端本地时间**，用户改时间就失效。

### 8.3 Cache-Control（HTTP/1.1，主流）

| 指令 | 含义 |
| --- | --- |
| `max-age=秒` | 缓存有效时长 |
| `no-cache` | **能用缓存但必须先协商验证**（不是不缓存！） |
| `no-store` | 真正的完全不缓存 |
| `public` | 中间代理也可缓存 |
| `private` | 仅浏览器可缓存（默认） |
| `s-maxage` | 共享缓存（CDN）的有效期 |
| `immutable` | 资源永不变（配合文件名 hash） |

::: warning 最高频误区
`no-cache` 不是「不缓存」，而是「缓存前要先问服务器」；`no-store` 才是彻底不缓存。
:::

**优先级**：Cache-Control > Expires。

## 九、协商缓存（发请求验证）

### 9.1 工作时序图

```text
浏览器                            服务器
  |                                  |
  | -- GET /app.js ----------------> |
  |    If-None-Match: "abc123"       |  比对 ETag
  |                                  |
  | <-- 304 Not Modified ------------ |  内容没变:
  |    (不返回资源体, 用本地缓存)        |  只回 304, 省 流量+带宽
  |                                  |
  | (资源更新后)                      |
  | -- GET /app.js ----------------> |
  |    If-None-Match: "abc123"       |  内容变了
  |                                  |
  | <-- 200 + 新资源 ----------------- |
  |    ETag: "def456"                |  新指纹
```

### 9.2 两种实现与优先级

| 方案 | 请求头 | 响应头 | 优缺点 |
| --- | --- | --- | --- |
| 时间戳版 | `If-Modified-Since` | `Last-Modified` | 轻量；秒级精度、改时间不改内容会误判 |
| **内容指纹版（主流）** | `If-None-Match` | `ETag` | 内容级精确；服务器要算 hash |

**优先级**：ETag > Last-Modified（同时存在先比 ETag）。

## 十、完整缓存决策流程

```text
发起请求
    |
    v
本地有缓存? -- 没有 --> 正常请求, 返回 200
    | 有
    v
强缓存字段计算 (Cache-Control.max-age / Expires)
    |
  有效 ----> 200 from cache (不发网络请求)  [强缓存]
    |
  过期
    v
发送协商请求 (If-None-Match / If-Modified-Since)
    |
    v
服务器比对资源指纹
    |
  没变 ----> 304 Not Modified (用本地缓存)  [协商缓存]
    |
  变了
    v
200 + 新资源 + 新 ETag / Last-Modified
```

### Memory Cache vs Disk Cache

```text
资源进入缓存后的去向:

  体积小 / 当前页面正在用 --> Memory Cache (内存)
                              快, 但关闭标签页就没了

  体积大 / 跨页面复用 ------> Disk Cache (磁盘)
                              稍慢, 但持久保存

刷新页面时 DevTools 里看到:
  小图片 / 脚本: 200 (from memory cache)
  大 CSS / 字体: 200 (from disk cache)
```

## 十一、实战缓存方案

```text
index.html            Cache-Control: no-cache                      协商缓存, 发版立即生效
app.a1b2c3.js         Cache-Control: max-age=31536000, immutable   一年强缓存
logo.a1b2c3.png       同上
```

原理：内容变 -> hash 变 -> URL 变 -> 当成新资源重新请求。**这就是打包工具给文件名加 hash 的原因。**

```text
发版流程图:
  部署新代码 -> app.js 内容变 -> 新文件名 app.x9y8.js
  用户请求 index.html -> no-cache 协商 -> 304? 变了! 返回新 HTML
  新 HTML 引用 app.x9y8.js -> 浏览器没缓存过 -> 请求新文件
  旧 app.a1b2c3.js 自然淘汰
```

| 完整请求流程？ | URL 解析 -> DNS -> TCP 握手 -> (TLS) -> HTTP 请求 -> 响应 -> 渲染 -> 挥手 |
| HTTP 和 HTTPS 的区别？ | 明文 vs 加密；80 vs 443 端口；HTTPS 需 CA 证书 + TLS 握手；解决窃听篡改冒充 |
| HTTPS 为什么既用非对称又用对称？ | 非对称安全但慢（换密钥），对称快（传数据），混合取长补短 |
| DNS 查询顺序？ | 浏览器缓存 -> 系统/hosts -> 本地 DNS -> 根 -> 顶级域 -> 权威（迭代） |
| 为什么三次握手？ | 确认双方收发能力 + 防止历史失效连接误建 |
| 为什么挥手四次？ | 被动方收到 FIN 后可能还有数据，ACK 和 FIN 需分开发 |
| HTTP/1.1 和 2 区别？ | 2 用二进制分帧实现多路复用 + 头压缩；1.1 有队头阻塞 |
| HTTP/3 用什么传输？ | QUIC（基于 UDP），解决 TCP 层队头阻塞 |
| 强缓存和协商缓存区别？ | 强缓存不发请求；协商缓存发请求，可能 304 |
| no-cache 和 no-store？ | no-cache 缓存前必须验证；no-store 完全不缓存 |
| 304 怎么产生？ | 带 If-None-Match/If-Modified-Since，服务器比对没变返回 304 |
| ETag 优先还是 Last-Modified？ | ETag 优先（内容级精确，但服务器有计算成本） |
| 文件名带 hash 为什么？ | 内容变则 URL 变，配合长强缓存既快又能立即更新 |

## 十三、速记卡

```text
1. 请求流程：DNS -> TCP 三次 -> (TLS) -> HTTP -> 缓存判定 -> 渲染 -> 四次挥手
2. HTTP 明信片, HTTPS 加密信封：非对称换密钥, 对称传数据, 证书防冒充
3. 三次握手定能力, 四次挥手因半关
4. 版本演进：1.1 keep-alive, 2 多路复用, 3 QUIC 抗丢包
5. 缓存：先强后协；no-cache 要验证, no-store 不缓存
6. ETag > Last-Modified；304 = 协商命中
7. hash 文件长强缓存 + HTML no-cache = 发版立即生效
```
